# v1.4.0 · 载荷守卫 + 标记守卫

两个新守卫，两条独立证据链：载荷守卫治"参数大到断流"（MALFORMED_RESPONSE），标记守卫治"调用写成了文本"（PTC 泄漏）。根因分析与取证见 `docs/TEXT-TOOL-CALL-LEAK.md`。

## 一、载荷守卫（src/args-guard.ts）

## 起因

某会话一个 `edit` 调用的参数 JSON 在 772 字符处断流（超长转义中文 `new_string`），宿主判 `Tool call "edit": Unterminated string in JSON` → `MALFORMED_RESPONSE`，turn 直接以错误结束：零重试、零纠偏。全会话统计（57 会话 / 272 turn-end）里该码只出现 1 次，但活跃会话上下文占用中位数 122k、p90 244k——大 payload + 高压力是常态，这是"低频高损"防线该管的形态。

物理解释决定了方案边界：该错误发生在**响应流组装期**，参数从未进入工具管道；宿主明确禁止 pre-dispatch 参数改写（`PreToolDecision` 注释 "Input rewriting is excluded"）。所以不"修形"，掰三个时刻。

### 新增（src/args-guard.ts + index.ts 接线四处）

- **事前·硬上限**（`tools/pre-execute` 第一分支，先于路径门、不限工具名单）：CJK 感知估算参数体积（汉字≈1 token、其他≈¼，与 dsh-infinite-context token-budget 同口径；估算器对 cap 提前截断，每次调用的成本恒为 O(cap)）。≥ 有效硬限 → 一行式 deny：报告估算值与限额，指示拆成 sequential 调用。上下文占用率（最近 `assistant/message` usage ÷ `requestContext().contextWindow`）≥ `pressureRatio` 时硬限自动乘 `pressureHardFactor`——高压下断流代价更大；占用证明不了就不缩放。
- **事中·软提醒**（`tools/post-execute` → `accept.additionalContexts`）：**成功**且参数 ≥ `argsSoftTokens` 的调用，随**下一请求**附带一行拆小指引——在断流之前掰模型行为。每 turn ≤2 条（随 `turn/start` 复位），失败/deny 结果不带。
- **事后·有限重试 + 纠偏**（`agent/request-error` / `agent/error`）：按码消费 `MALFORMED_RESPONSE`（宿主内置码，此前全生态零消费）：按会话计数，`malformedRetry` 次内先 `agent.inbox.append('next-step', 纠偏文案)` 再返回 `{kind:'retry'}`；重试关掉（`0`）则走 `agent.inject` 每 turn 一次。纠偏文案自带防误伤措辞（"改动已落盘则忽略"）——nudge 同样会到达重试**成功**后的下一步。turn 以 `completed` 收尾即清零计数（可见进展）。
- 两个 LRU 跟踪器（`MalformedStreak`/`NudgedTurns`）保证重试有限、每 turn 只纠偏一次；`tools/result` 观察器同时忽略 `Error: payload-guard` 回灌，载荷拒绝不会污染零结果 streak。

### 配置（全部 `numeric()` 告警回退）

| 键 | 默认 | 语义 |
|---|---|---|
| `argsHardTokens` | 8000 | ≥ 即 deny；0 关本层 |
| `argsSoftTokens` | 2500 | 软提醒阈值；0 关；>硬限自动夹到硬限 |
| `pressureRatio` | 0.75 | 收紧触发占用率；0 关自适应 |
| `pressureHardFactor` | 0.5 | 收紧系数（高压下硬限→4000）；`0` 或 `≥1` 不收紧 |
| `malformedRetry` | 1 | MALFORMED 有限重试；0 只纠偏不重试 |

**共存注意**：若同时安装 dsh-llm-retry，勿把 `MALFORMED_RESPONSE` 加进其 `retryableCodes`——本守卫已按码有限重试，叠加会双重重试。

## 二、标记守卫（src/markup-guard.ts，依据 docs/TEXT-TOOL-CALL-LEAK.md）

### 起因

session f2415117（2026-11-26 取证）：PTC 部署的 API 面只有 `run_code` 一个工具，模型的原生调用语法一旦发出就必然退化为纯文本。该会话单轮 31 step 泄漏 5 次死标记（`skill`×2、`read`×2、`todo_write`，共 1592 字符永久留驻上下文），全部是"合法 run_code 块 + 泄漏标记"的**混合消息**——宿主防线 `text-tool-call.ts:86` 的门控"消息含任一调用块即豁免"把 5 次全放过（其"标记只是调用周围叙述"的设计假设被 PTC 混合形态证伪），模型收不到任何"未执行"反馈，跨 20 step 重复同一错误。泄漏目标全部是 `<available_tools>` 直调式清单里的原生工具名，34/34 成功调用则是清单里没有的 `run_code`——"清单里写了就直调"的预训练惯性压过 PTC 约定，是诱导层根因。宿主防线本身是本地补丁（曾随 checkout 更新整文件丢失），插件侧防线必须能独立存在。

### 新增（两个层面，均在插件可落地边界内）

- **A2 · 常驻约定（提示层，治本）**：`systemPrompt.context()` 在每步刷新的系统提示快照注入 `[ptc-call-convention]`（order 118，SANDBOX_POLICY 与 SUBAGENT_DELEGATION 之间的策略簇）——`run_code` 是唯一直调工具，清单里的其余工具只能在 run_code 内 `await tools.name(args)`；与宿主静态 `tools:ptc-only` 段语义一致，但位置离泄漏发生点更近，对抗长上下文中的指令衰减。
- **B · 泄漏纠偏（检测层，兜底）**：`session/event(assistant/message)` 缓存本 turn 最新消息的文本块与 turn 号 → `agent/pre-step` 检测命中 → 在 step 消息尾部追加一条预算内纠偏 user 消息（指名未执行 + `await tools.name(…)` 补做路径；第 2 条起带 `markup-leak #N` 升级文案）。检测语义逐字复用宿主 `text-tool-call.ts` 的已踩坑结论并**去掉调用块豁免**；fenced/inline code 内标记剥除后才搜索（宿主 fence 闭合正则实际要求 ≥5 反引号、fence 打开即吞尾——宁可漏检不错纠，逐字节保留并测试钉住）。
- **预算与时效**：每 turn ≤ `markupBlock` 条防纠偏自身成为噪音；已结束 turn 的旧泄漏视为过期意图不追纠（turn 匹配门）；本 turn 见到干净消息即清零升级计数。追加走 `{...decision, messages: [...]}`（tool-skill 同款形状）——waterfall 兜底 handler 闭包引用原始 claimed 消息，改 args 无效。

### 配置

| 键 | 默认 | 语义 |
|---|---|---|
| `markupBlock` | 2 | 每 turn 最多注入的纠偏条数；`0` 关闭标记守卫 |
| `markupMinChars` | 40 | 泄漏标记段最短长度（宿主防线同值），低于此视为叙述残片 |

## 周边

- pack.sh / pack.ps1 tarball 必含清单补齐 `dist/repeat-guard.js`（1.3.0 起的已知校验缺口）、`dist/args-guard.js` 与 `dist/markup-guard.js`。
- **pack.cmd 修复**：`pack.ps1` 补 UTF-8 BOM——`pack.cmd` 走 Windows PowerShell 5.1，无 BOM 的 UTF-8 中文按 GBK 误读、乱码吞掉引号导致语法解析失败（此坑一直在，以往发布都走 `pwsh` 入口；BOM 是 5.1/pwsh 双入口唯一安全的编码）。
- 跨包词表：session-tools `error-audit.ts` 的 `isGuardDenial` 增加 `payload-guard:` 锚点——新拒绝归入 guard 拒绝分账，不进错误分母（标记守卫注入的是纠偏消息而非拒绝，无需锚点）。
- wiki/01–04 对齐到 src 现况（01 决策流补载荷层与零结果锁、新增载荷守卫机制节 §6 与标记守卫机制节 §7；02/03 从 1.0.x 形态补齐 repeat-guard、args-guard、markup-guard 的模块/API 导读；04 配置表补全）。
- 标记守卫接线核实过两处宿主合同：`agent/pre-step` 载荷类型为 `UserMessage[]`（inbox claimed，不含历史 assistant 消息——检测输入经 `session/event` 缓存获得）；`agent/request-error` 的失败字段名为 `failure`（`agent/error` 才是 `error`），`LlmFailure.code` 为 string。

## 验证

- typecheck、build 绿；测试 40→89 全绿（`tests/args-guard.test.ts` 14 例 + `tests/markup-guard.test.ts` 19 例纯函数：三形态命中、误报集、宿主 fence 语义钉住、预算与升级；`tests/index.test.ts` 14→23 例接线级：载荷守卫 + 标记守卫注入/turn 门/预算耗尽/关闭键/reject 不花预算/systemPrompt 注册门控、配置回退、`disabled:true` 不注册）。
- 冒烟建议（宿主开发组合直挂 dist）：≈5k token write → 结果尾部随下一请求带软提醒；≈12k token → 一行 `Error: payload-guard:` 拒绝、拆两次可过；真触发一次断流 → attempt 记录里一次重试 + inbox 纠偏行。标记守卫：同部署同档位发起"加载 skill + 读文档 + 写 todo"类任务（本次泄漏的三个意图），若模型再写死标记，下一步头部应出现 `[Guard check — the tool call in your previous message never ran]` 纠偏，且意图以 run_code 补做。
